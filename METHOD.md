## 1. Цель

Исследовать, возникает ли между независимыми узлами
(LLM и человеком) нечто, чего нет ни в одном из них.

Не «какая модель лучше». Не «какой ответ правильный».
А: что появилось в процессе взаимодействия такого, что
нельзя полностью свести к исходному материалу.

## 2. Мета-принцип

См. CONCEPT.md, раздел «Мета-принцип». Здесь не дублируется.

Короткая форма: концепция не обязана вести к одной реализации.
Её задача — увеличивать пространство возможных реализаций.

## 3. Формат передачи

Один узел → оператор → следующий узел.

Правила:

- Узлы не видят ответы других до того, как дали свой.
  Это операторская дисциплина, не техническое ограничение.
  Нарушение фиксируется в trace.md как операторское
  действие — это тоже данные.
- Оператор может редактировать, сокращать, менять порядок.
  Каждое такое действие фиксируется.
- Задержка между узлами фиксируется, если значима.
- Порядок узлов фиксируется.
- Асимметрия узлов. Узлы выбираются не для дублирования,
  а для асимметрии: LLM для масштаба и поиска паттернов,
  человек для контекста и этической валидации, и так далее.
  Оператор обязан зафиксировать, почему для этого шага
  выбран именно этот узел.

- Кумулятивный контекст. Если эксперимент предполагает
  взаимодействие узлов (не изоляцию), каждый узел получает
  ответы предыдущих. Что именно получил каждый узел —
  фиксируется в trace.md отдельным блоком «Что передано»
  для каждого узла. Это часть условий эксперимента,
  не деталь.

- Асимметрия доступа. Узлы могут иметь разные инструменты:
  одни читают внешние URL, другие — нет. Это фиксируется
  в поле «Примечание (доступ к репо)». Узел, не имеющий
  доступа к общему артефакту, не может считаться равным
  другим узлам в этом эксперименте.

## 4. Роль оператора

Оператор — не прозрачный посредник. Это участник.

Его решения (кого спросить, что передать, в каком порядке,
что опустить) — часть эксперимента. Действия оператора
фиксируются наравне с ответами узлов. В trace.md есть
отдельный раздел HUMAN.

Оператор действует в паре с LLM-ассистентом. Ассистент
генерирует команды, черновики правок, синтезы; оператор
выполняет, проверяет, принимает решения. Эта пара —
единая роль оператора, не два отдельных узла. Ассистент
фиксируется как условие эксперимента, не как участник.

## 5. Формат записи (trace)

Один файл на один эксперимент. Append-only.
Ничего не стирается.

    <Заполняется, если эксперимент претендует на L3.

    Ответ:

## 5.1. Процедура baseline

Baseline — изолированный прогон узлов на исходном input
без взаимодействия. Применяется, когда эксперимент
претендует на L3.

### Когда проводится

- Если эксперимент предполагает заявку на L3 —
  baseline обязателен.
- Проводится ДО Round 1 (pre-baseline). Не после.
- Если эксперимент не претендует на L3 — baseline
  не обязателен.

### Как проводится

1. Оператор фиксирует точный input.md и его хэш.
2. Для каждого узла открывается новая чистая сессия:
   без истории, без других узлов, без упоминания
   эксперимента, без Target.
3. В сессию передаётся строго input + нейтральная
   инструкция: «Ответь на этот input. Не используй
   внешний контекст. Других участников нет.»
4. Ответ фиксируется дословно, без редактуры.
5. Сессия закрывается.
6. Для LLM выполняется двойной прогон — два новых
   чистых чата с тем же input. Это контроль
   стохастической вариативности.

### Что фиксируется

В trace.md добавляется блок ## Baseline с полями:

- узел;
- session: new / closed;
- время;
- хэш input;
- точный input;
- полный ответ;
- для LLM — оба ответа (Run 1, Run 2).

### Ограничение

Baseline не может быть проведён постфактум — после
Round 1 или после появления кандидата. При одном
операторе знание результата загрязняет слепоту.
Основание: 004 и 007 показали, что постфактум-baseline
не работает.

## 5.2. Шкала воспроизведения

Шкала применяется при сравнении baseline-ответов с Target.
Устраняет расхождение семантики, обнаруженное в 004.
Основание: консенсус 006, подтверждён 007.
Расширена состоянием PARTIAL по итогам 008 и 009.

### Объект оценки и сравнения

- Объект оценки: изолированный вывод узла (артефакт).
- Объект сравнения: кандидат, представленный заранее
  зафиксированными критическими атрибутами (не более 5).

### Двухуровневая модель

Шкала имеет два уровня, которые нельзя смешивать:

- Семантика шкалы. Объект сравнения — заранее
  зафиксированные критические атрибуты. Это часть
  определения шкалы.
- Процедура. Когда, кем и где атрибуты зафиксированы —
  отдельное процедурное условие эксперимента.

Без модификатора «заранее зафиксированные» оператор
может выбрать атрибуты ad hoc в момент оценки. Тогда
YES становится самоисполняемым — оператор подбирает
атрибуты под ответ. Это недопустимо.

### Четыре состояния

- YES: все заранее зафиксированные критические атрибуты
  явно присутствуют в выводе. Каждый можно прямо
  процитировать без догадок.

- PARTIAL: одна или несколько заранее зафиксированных
  критических атрибутов воспроизведены явно и
  положительно, но не все. Результат структурно
  родственен Target (та же операция, другая ось;
  та же структура, другое содержание), но Target
  в целом не воспроизведён.

  Отличие от YES: не все атрибуты.
  Отличие от NO: есть положительно установленное
  совпадение хотя бы с одним зафиксированным атрибутом.
  Отличие от AMBIGUOUS: данные достаточны,
  совпадение установлено.

- NO: ни один из атрибутов не присутствует, либо вывод
  содержит явный отказ, сброс контекста или ответ
  на другой вопрос.

- AMBIGUOUS: данных недостаточно, либо вывод содержит
  неустранённые противоречия, либо оператор не может
  однозначно установить соответствие.

### Правило разрешения неопределённости

При сомнении между YES/PARTIAL/NO и AMBIGUOUS —
AMBIGUOUS. Это правило разрешения, не содержательный
критерий.

При сомнении между PARTIAL и NO — если совпадение
с зафиксированным атрибутом нельзя процитировать
прямо, это NO или AMBIGUOUS, не PARTIAL.

### Что не оценивается

Слово YES/NO самого узла не является доказательством
состояния. Оценивается содержание вывода, не самооценка.

### Основание для PARTIAL

Эксперименты 008 и 009 показали: AMBIGUOUS смешивал
два разных случая — отсутствие данных и наличие
частичного совпадения. PARTIAL разделяет эти случаи.

Основание: консенсус 008 (все четыре узла — за PARTIAL),
синтез 009, первое применение в 010.
Основание различения уровней (прогон vs агрегация)
приведено в разделе 5.3.

## 5.3. Процедура baseline-проверки L3-кандидата

Применяется, когда эксперимент дал L3 CANDIDATE.
Проверяет, воспроизводится ли ключевой элемент кандидата
в изоляции. Если да — кандидат понижается до L2.
Если нет — кандидат подтверждается как L3.
Основание: 004, 007 (подтверждение), 010 (опровержение).
Обновлено по итогам 009 и 010.

### Target

Target — ключевой элемент L3-кандидата. Не вся процедура,
не все элементы. Один конкретный элемент, который
возник во взаимодействии и, предположительно, недоступен
в изоляции.

Фиксируется в trace.md до начала baseline-прогонов.

### Input для baseline

Тот же input, на котором возник L3-кандидат.
Не новый. Не изменённый. Тот, что был в исходном
эксперименте.

### Прогоны

4 узла × 2 прогона = 8 baseline-прогонов.
Для каждого узла — новая чистая сессия, без истории,
без других узлов, без Target.

### Два уровня классификации

Состояние отдельного прогона и итоговый вердикт серии —
РАЗНЫЕ УРОВНИ. Их нельзя смешивать.

Уровень 1 — классификация прогона.
Каждый baseline-ответ получает одно из четырёх
состояний по шкале воспроизведения (раздел 5.2):

- YES: Target воспроизведён.
- PARTIAL: воспроизведена часть заранее зафиксированных
  атрибутов, но не Target целиком.
- NO: совпадения нет.
- AMBIGUOUS: данных недостаточно или есть
  неустранённые противоречия.

Уровень 2 — агрегация серии.
Правило агрегации задаётся ОТДЕЛЬНО. Оно не выводится
автоматически из определения отдельных состояний.

Основание: консенсус 009 (Luna ввела различение,
Grok подтвердил). Первое применение — 010.

### Правило агрегации серии

Базовая таблица:

- все YES → итог YES.
- все NO → итог NO.
- все PARTIAL → итог PARTIAL.
- есть хотя бы один AMBIGUOUS без достаточного
  основания для другого итога → итог AMBIGUOUS.
- смешанные случаи → отдельное правило (см. ниже).

Правило для смешанных случаев:

- YES хотя бы у одного, остальные YES/PARTIAL →
  итог YES (полное воспроизведение подтверждено
  хотя бы один раз, при отсутствии NO/AMBIGUOUS).
- YES хотя бы у одного, есть также NO или AMBIGUOUS →
  итог AMBIGUOUS (нестабильное воспроизведение).
- PARTIAL хотя бы у одного, остальные PARTIAL/NO →
  итог PARTIAL (есть установленное частичное совпадение,
  полного нет).
- PARTIAL + AMBIGUOUS без YES → итог AMBIGUOUS
  (неопределённость не снята).

Правило действует, пока не появится второй случай,
требующий уточнения.

### Особый случай — автор различения

Если Target — различение, введённое конкретным узлом
в предыдущем эксперименте, и YES даёт тот же узел
в baseline-прогоне, это НЕ считается независимым
воспроизведением.

Основание: 010 — Luna ввела различение в 009,
Luna Run 2 воспроизвела его в 010. Формально YES,
содержательно — воспроизведение собственной работы.

В таком случае:

- L3-кандидат понижается до L2 по формальному правилу.
- В trace.md фиксируется особый случай.
- Если требуется строгая проверка L3, рекомендуется
  повторный baseline-прогон с исключением узла-автора
  из состава. Если после исключения все NO —
  L3-кандидат подтверждается.

Правило введено по итогам 010. Требует подтверждения
на втором случае.

### Что фиксируется

Блок ## Baseline Assessment в trace.md:

- для каждого прогона: Reproduction (YES/PARTIAL/NO/AMBIGUOUS),
  Evidence, Missing elements.

Блок ## L3 Check:

- итоговый вердикт с указанием правила агрегации.

Блок ## Level Assignment:

- статус кандидата (подтверждён / понижен / не определён)
  и особый случай (если применим).

Блок ## Operator Notes:

- наблюдения по ходу эксперимента.

## 6. Версионирование

- input.md не меняется после старта эксперимента.
- Любые правки задачи идут только через новый эксперимент
  или через явную запись в trace.md с пометкой оператора.
- trace.md — append-only. Не стирается, не перезаписывается.
- Отдельные правила append-only и версионирования input
  дополняют друг друга, не конфликтуют.

## 7. Градация результата

Не всякий результат — candidate emergence. Введена шкала:

- L0 — нет изменения. Результат = input.
- L1 — рекомбинация. Сумма ответов узлов без преобразования.
- L2 — frame shift. Изменился способ видеть задачу, но
  источник прослеживается к одному узлу.
- L3 CANDIDATE — кандидат на emergence. Паттерн или вывод,
  который предположительно невозможно получить в изоляции,
  но baseline-проверка ещё не проведена.
- L3 — подтверждённый emergence. Прошёл baseline-проверку
  (раздел 5.3): ключевой элемент не воспроизведён ни одним
  узлом в изоляции.

Большинство экспериментов будут L1–L2. Это не провал,
это данные.

### Уточнение критерия L3

Критерий «невозможно получить, скормив исходный input
любому из участвовавших узлов в изоляции» работает
на уровне КОНКРЕТНОЙ ФОРМЫ паттерна, не базовой идеи.

Основание: в 007 Luna Run 2 показала, что общая идея
разделения (шкала vs тест+условия) доступна в изоляции,
но конкретная двухуровневая форма (семантика vs
процедура) — нет. Значит, L3 может подтверждаться
для конкретной формы, даже если её базовая идея
доступна в изоляции.

### Уточнение по PARTIAL

Введение PARTIAL в шкалу воспроизведения (раздел 5.2)
расширяет градацию результатов baseline-проверки.

При наличии PARTIAL в baseline-прогонах:

- PARTIAL не означает YES. Кандидат НЕ воспроизведён
  полностью.
- PARTIAL не означает NO. Установлен родственный
  компонент — структурное совпадение с частью Target.
- PARTIAL в агрегации серии (раздел 5.3) даёт отдельный
  итог, отличный от YES/NO/AMBIGUOUS.

Основание: 010 — первый эксперимент с реальным
применением PARTIAL. Результат: 1 YES, 5 PARTIAL,
2 NO, 0 AMBIGUOUS. PARTIAL дал градацию, которой
не было бы по трёхзначной шкале.

### Правило присвоения L3

L3 не присваивается без baseline-проверки. Без неё
результат остаётся L3 CANDIDATE. Переход от L3 CANDIDATE
к L3 фиксируется в блоке ## Level Assignment trace.md
с обоснованием.

### Особый случай — автор различения

Если Target L3-кандидата — различение, введённое
конкретным узлом в эксперименте, породившем кандидата,
и в baseline-проверке YES даёт тот же узел, это
НЕ считается независимым воспроизведением.

Формально L3-кандидат понижается до L2. Содержательно
случай требует разбора: воспроизведение собственной
работы не то же самое, что независимое воспроизведение
другим узлом.

Основание: 010 — Luna ввела различение в 009,
Luna Run 2 воспроизвела его в 010.

Решение для строгой проверки: повторный baseline-прогон
с исключением узла-автора. Если после исключения
все NO — L3-кандидат подтверждается. Правило введено
по итогам 010, требует подтверждения на втором случае.

### Что не присваивается

L3 не присваивается автоматически даже при агрегации
PARTIAL. PARTIAL даёт отдельный статус, но не заменяет
baseline-проверку L3.

Если итог baseline-проверки — PARTIAL, это означает:
установлено частичное совпадение, но полного
воспроизведения нет. L3-кандидат понижается до L2,
но с фиксацией частичного совпадения в trace.md.

## 8. Критерий опровержения

Эксперимент не подтверждает emergence, если результат:

- полностью выводится из ответа одного узла,
- является суммой ответов узлов без преобразования,
- воспроизводится в одном узле без взаимодействия.

Отсутствие candidate emergence в первых 10–20 экспериментах
не опровергает гипотезу. Но если после 50 экспериментов с
разными конфигурациями узлов, input'ов и порядков не появляется
ни одного L2 или L3 — это основание пересмотреть метод,
не гипотезу.

## 9. Критерий завершённости эксперимента

Эксперимент считается завершённым, когда выполнено хотя бы одно:

- узлы прошли все запланированные раунды;
- достигнут L2;
- достигнут L3 CANDIDATE;
- оператор принял решение о завершении (с фиксацией причины);
- истёк согласованный срок (если был задан на старте).

«Дотягивание» эксперимента до более высокого уровня — не
приветствуется. Если результат L1 — он фиксируется как L1.

### Особый случай: L3 CANDIDATE и L3

Если эксперимент дал L3 CANDIDATE, он завершён
как эксперимент, но порождает следующий:

- baseline-проверка (раздел 5.3) — отдельный эксперимент;
- при подтверждении — L3 фиксируется в итоговом trace
  baseline-проверки, не в исходном.

Это значит, что L3-кандидат требует ещё одного
эксперимента для перехода в подтверждённый L3.
Основание: 004 и 007.

L3 подтверждается только после завершённого
baseline-процесса. Без него — L3 CANDIDATE.

## 10. Candidate emergence — что помечается

L3 CANDIDATE помечается, если:

- результат изменяет frame задачи или порождает новый
  вопрос;
- результат не сводится полностью к ответу одного узла;
- существует ключевой элемент, предположительно
  недоступный в изоляции.

Ключевой элемент фиксируется явно — он становится Target
для baseline-проверки (раздел 5.3).

Что не помечается:

- «интересный ответ»,
- «неожиданный результат»,
- «все согласились»,
- «сильный ответ одной модели».

Оценочные слова к emergence не применяются.
Воспроизводимость проверяется через baseline, не через
повторный проход. Основание: 004 и 007 показали, что
повторный проход не различает emergence и рекомбинацию.

## 11. Если эксперимент ушёл в сторону

Если в процессе возник вопрос за рамками исходного input —
это не сбой. Это порождение нового input. Зафиксировать в
разделе Next как отдельный эксперимент NNN+1. Не пытаться
впихнуть всё в один trace.

## 12. Открытые вопросы метода

Решено в v3:
- статус PARTIAL → раздел 5.2 (четвёртое состояние);
- различение уровня прогона и уровня агрегации →
  раздел 5.3 (два уровня классификации);
- особый случай «автор различения» → раздел 5.3 и 7
  (правило понижения до L2, рекомендация повторной
  проверки без автора).

Остаются открытыми:
- накопление контекста внутри одной сессии;
- один оператор или несколько;
- верхняя граница «намеренной малости» проекта;
- разрыв «формальное правило → содержательный вывод»
  (007, см. meta/open-questions.md);
- формализация паттерна нестабильности узлов
  (Qwen 004/005/007, Luna 010);
- градация доступности Target по узлам (010);
- правило «автор различения» требует второго случая
  для подтверждения.

Актуальный список открытых вопросов — в
meta/open-questions.md. Здесь фиксируются только те,
что относятся к самому протоколу.
